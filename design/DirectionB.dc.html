No Work band: subtasks:false, agentAssignable:false. No Date chip: dateAnchored:false. Times per day appears: counters.dailyCounts. Nothing branches on 'habit' to make any of that true.
Why
Because CLAUDE.md already says it: code that wants to branch on task vs habit should ask the registry a capability question. Every chip obeys that; the layout does not, and the layout is what the user reads. Bands make adding a type free at the layout level too — a custom type declares subtasks: true and gets a Work band with no design decision. And the three container roles stop being invisible: filed / gated by / serves is exactly what classify, gate and aspire mean, said in words a user can act on rather than as five identical chips in a row.
Tradeoff
Bands cost vertical space and reading. Four headings on a 420px column is four lines that carry no data, and on a fresh task with two live bands the headings outweigh what they label — this direction is worst exactly where A is best. It also asks the user to learn a vocabulary they never requested: gated by is a true and useful word, and it is also a new one. Finally the axes are a judgement, not a fact in the code — the registry has no "axis" field today, so this direction has to add one, and someone has to decide where Priority lives.
Sidebar and full page: two surfaces, one grammar
Same bands both places; the page lays them in two columns instead of one and adds the thread beside them. That is a real difference in job — a column count, not a feature set — and it makes the doubling impossible to ship, because there is no longer a static rendering to go stale beside a live one: the page's chips are the editable chips, and Edit stops opening a panel over the page at all. That deletes withDetailSections and the page's locally-mounted second ItemDialog.
