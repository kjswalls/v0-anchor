Keyboard shortcuts

Every binding, rebindable. The same table ⌘/ opens.

Open

One record. The pane is real, deep-linkable and searchable — and it holds a button, not a setting.

What it is

A 512px dialog rendered from DEFAULT_SHORTCUTS, which is derived statically from STATIC_COMMANDS plus two shell bindings. 19 rows, grouped by the command registry's own headings, each row a click-to-record key button. Overrides persist by shortcut id in localStorage; labels always come from the registry.

Why it is being questioned

1. The pane is a door. Settings search can find the row "Keyboard shortcuts" and then hands you a modal it cannot see inside. Type "undo" into settings and nothing answers.

2. Nineteen flat rows, no filter. Every other configuration surface in the app got search, per-row reset and a modified marker. This one has reset-all and nothing else.

3. A binding can be dead and look alive. The dispatcher checks isAvailable() before it runs anything. The modal never asks. A key whose command is switched off, or wrong for the current view, renders exactly like one that works.

The live loose end

Extension gating shipped with "off means inert, but still findable". The palette honours that — a switched-off command greys. The shortcuts modal has no availability channel at all, so it is the one surface where inert and live are indistinguishable. Every direction below has to answer for that.

Drawn against app/globals.css light tokens — paper/well ramp, cool hairline border, lime accent, the soft-lg dialog shadow, 406px sidebar geometry.
