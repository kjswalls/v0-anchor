Eight of nineteen have no row to hang on

⌘K Search / Commands ⌘I Quick add ⌘[ Toggle sidebar ⌘\ Focus item panel ⌘A Select all E Edit hovered ⌫ Delete hovered

Six are hidden: true by design — a row for "focus the omnibar you are typing in" is nonsense — and two are SHELL_SHORTCUTS, which act on the item under the mouse and have no palette row at all.

Why

It is the most Anchor-shaped answer on the canvas: one registry, one surface, no third list. A binding is seen at the moment you use the command, and rebound at the moment you think "I do this constantly, it should be one key". It deletes a component, a dialog slot, and the floating ⌘/ badge, and it is the only direction that reduces the number of places a shortcut is described.

Tradeoff

Two, and the second is close to disqualifying.

The palette cannot answer "what are my shortcuts". It is a query-filtered list — there is no state in which all nineteen are on screen, and no way to see that a key is free. The conflict check (refuse a combination another binding already answers to) needs the whole set the palette is not showing.

Eight bindings have no row. Fixing that means a bindings-only mode that ignores hidden and splices in SHELL_SHORTCUTS — at which point it is a table living inside a palette, wearing a palette's constraints for none of a palette's benefits.

The dead key

Already solved here, and only here. isAvailable() greys the row today; a switched-off command is inert but still findable, which is the posture the extension work asked for. Whatever else is decided, this is the behaviour to copy.

Buildable, with a hole. Nothing here threatens the frozen ids — but note what this direction promises and cannot deliver: "bind anything you can see" is blocked, because only STATIC_COMMANDS may own a shortcut.
