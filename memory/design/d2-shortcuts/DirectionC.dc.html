Why

This is the shape Anchor already uses for exactly this problem. The omnibar is one component in two shells — a resting dock and a summoned launcher, differing only in emphasis, Enter semantics and copy. A binding list is the same situation: one canonical place that search, deep links and the rail can point at, and one summoned frame for the moment you are actually holding the keyboard. Neither frame owns the data, so neither can drift.

Tradeoff

It inverts a dependency. SettingRow is written against SettingCtx, which today only /settings assembles — so the planner shell would import settings machinery to render a dialog. That is survivable precisely because a binding record needs nothing from that context (it reads and writes the override store), but "survivable" is not "free", and it is the one line on this canvas that a reviewer will push back on. There is also a real layout bend: the pane's 132px control column is the source of its calm, and a 512px dialog cannot afford it.

The dead key

Inherited from B, and better for being inherited: one unavailable() written once now reads correctly in both frames. The failure mode where two surfaces disagree about whether a key is live cannot occur.

Buildable. Strictly B plus a second renderer. The extra cost is one component and one honest import, not a second source of truth.
